## 一、TL;DR

> 当前系统是**内核强、外壳弱**：混合检索、多轮改写、流式生成、ACL + 审计四块地基已相当扎实，但**产品外壳（管理 UI、权限体系、部署、溯源、评测）几乎为零**——这正是"卖不出去"的真正原因，而不是代码写得不够好。
>
> 最快售卖路径 = 死守**政务 / 中小企业"轻量私有化 + 答得准 + 可审计"**象限，先补齐 P0 六件套，再补**检索精排（Rerank）**与**中文评测集**这两项"能证明效果"的关键资产。

---

## 二、现状盘点：什么已经有了，什么真正缺

| 维度 | 现状 | 判定 |
|---|---|---|
| 检索内核 | FAISS 稠密 + BM25 稀疏 + 手写 RRF + jieba 中文分词 | ✅ 扎实，可直接复用 |
| 对话能力 | 追问改写（condense）+ 最近 3 轮历史 | ✅ 可用 |
| 生成体验 | SSE 流式、LLM/Embedding 解耦（本地 Embedding + 可切换 LLM） | ✅ 扎实 |
| 权限与审计 | 文档级 ACL、检索前裁剪、拒答、JSONL 审计 | ✅ **差异化内核已有** |
| 产品外壳 | 管理 UI、账号体系、文档上传、引用溯源、部署脚本 | ❌ **几乎空白** |
| 效果证明 | 中文评测集、准确率基线、回归门禁 | ❌ **完全空白（售卖硬伤）** |
| 工程化 | 容器化、可观测性、CI/CD、缓存、多租户 | ❌ 空白 |
| 规模能力 | 单进程、本地文件索引、内存态 BM25 | ❌ 仅单机原型 |

**关键判断**：代码质量不是瓶颈。瓶颈是「**卖相**」与「**可证明的效果**」——客户看不到管理界面，也无法被说服"你的系统答得准"。

## 三、合并路线图：三阶段 × 双线

### 🟢 阶段一 · MVP（可售卖试点）— 关门条件

**目标**：能装进客户内网、能演示、能被验证答得准。

| 线 | 内容 | 负责人视角 | 验收 |
|---|---|---|---|
| **产品线（P0）** | 多格式解析 + 知识库管理 UI；账号/角色权限打通现有 ACL；答案引用溯源；审计日志可导出；Docker Compose 一键部署 | 许清楚 | IT 30 分钟内拉起；越权查询返回空集；每个回答可点开原文 |
| **技术线** | RRF 后插入 **Cross-Encoder Rerank**（本地 `bge-reranker-v2-m3`）；cosine 距离 + Rerank 分数双判门禁；建 ≥100 条中文离线评测集（Recall@5 / 拒答准确率 / 引用准确率）；父子分块试点 | 高见远 | Recall@5 有基线数据；docker compose 即可完整演示 |

> **为什么 Rerank 是第一刀**：现有链路只有 RRF 融合，**没有精排**——这是"答不准"的主要技术根因。本地 reranker 零 API 成本、时延仅 30–80ms、离线可用，性价比远高于换向量库。

---

### 🟡 阶段二 · 生产级（可规模化交付）

**目标**：能被反复部署、能运维、能防回归。

| 线 | 内容 |
|---|---|
| **产品线（P1）** | 检索调优面板（chunk 大小 / 阈值 / RRF 权重可配）；多知识库隔离；对话历史持久化与导出；答案反馈（badcase 收集数据飞轮）；模型热切换 UI；prompt injection 基础防护 |
| **技术线** | 异步摄取流水线（上传即 202，Worker 后台跑）；**语义/检索/embedding 缓存（语义缓存必须带 tenant_id + acl_signature 隔离）**；可观测性（OTel + 自托管 Langfuse + Prometheus）；CI/CD 含 **RAGAS 评测门禁**（指标降 >3% 阻断发布）；向量库沿用 pgvector；API 无状态 + Worker 水平扩展；成本时延看板 |

---

### 🔵 阶段三 · 规模化（SaaS / 复制）

**目标**：多租户、能扛量、能自动扩缩。

| 线 | 内容 |
|---|---|
| **产品线（P2）** | 文档自动摘要与标签；IM 入口（企微 / 钉钉机器人）；移动端适配；可视化检索过程；知识库健康检查 |
| **技术线** | SaaS 多租户（row-level `tenant_id` + 向量 payload 过滤，政务大客户走独立部署）；向量库切 **Qdrant**（分片 + 副本 + 量化压内存 1/4）；K8s 自动扩缩容；在线质量闭环（轨迹采样 + LLM-as-judge）；信创适配；容量规划（千万~亿级） |

---

## 四、贯穿全程的四条铁律

1. **不推翻已有设计**：`main.py` 不动；`app/` 的 ACL / 审计与 `ingest/` 摄取子系统是两座已验证的地基，全部复用。
2. **权限层永远在检索层之前**：先按用户裁剪候选集 → 再检索 → 最后生成；无依据直接拒答，不调用 LLM。
3. **评测是售卖前提**：无中文离线评测集 + CI 门禁，"效果"既无法证明也无法防回归——这是当前最大的售卖硬伤。
4. **缓存是降本第一杠杆**：语义缓存命中每 +10% ≈ LLM 成本 −10%；但**缓存必须带 scope 隔离**，否则跨租户泄露。

## 五、需要你拍板的关键决策点

按影响面排序，**前 3 个不定，后面所有选型都会返工**：

| # | 决策点 | 选项 | 影响 |
|---|---|---|---|
| **1** | **交付形态** | ① 私有化单机为主 ② SaaS 多租户为主 ③ 并行 | 决定向量库（pgvector vs Qdrant）、隔离级别（row-level vs 独立部署）、投入分布 |
| **2** | **首选目标市场** | ① 政务 / 国企 ② 中小企业 ③ 专业机构 | 决定 P0 重心（政务需 SSO、等保、密评；中小企业需一键部署与轻量） |
| **3** | **商业化路径** | ① 开源引流 + 企业版收费 ② 纯闭源授权 ③ 纯开源换影响力 | 决定社区建设投入、文档质量要求、销售物料策略 |
| 4 | 知识库规模预期 | 百 MB / GB / 十万文档级 | GB 级以上须放弃 FAISS 单机方案 |
| 5 | LLM 默认策略 | 捆绑本地 Ollama / 主推客户自带 API | 影响部署复杂度与"零成本"叙事 |
| 6 | 合规门槛 | 政务是否必须等保 / 密评、是否彻底禁外联 | 决定在线 LLM 能否使用、是否只能本地部署 |
| 7 | 算力预算 | 接受本地 GPU / 必须在线 LLM | 决定成本结构与私有化可行性 |
| 8 | SSO / 多租户是否进 P0 | 是 / 否 | 政务与国企基本为必选项 |
| 9 | 商业化计费模式 | 私有化授权 / 实施费 / SaaS 席位 / token | 影响缓存与成本看板的权重设计 |
| 10 | 数据源范围 | 是否纳入网页 / 邮件 / PPT / 数据库 Text-to-SQL | 影响摄取子系统工作量 |

## 六、建议的三个下一步动作

1. **先拍板上表 #1–#3**（形态 / 市场 / 商业化）。这三个决策直接决定阶段一 P0 的功能取舍。
2. **立即启动"能证明效果"的两件事**：建 ≥100 条中文离线评测集 + 接入本地 Rerank。这是唯一能把"我觉得答得准"变成"客户能验收的数字"的动作，也是当前最大的价值洼地。
3. **准备销售武器**：一套"政务合规演示包"——脱敏样例数据 + Docker 一键拉起 + 10 分钟看到带引用、带审计的答案。技术能卖的是"当场可验证"，不是 PPT。

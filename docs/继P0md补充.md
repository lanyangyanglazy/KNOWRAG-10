## 1. 前提：P0 计划仍按 v0.1 编写，有 8 处不同步

若不先对齐，P0 会"按计划交付、按设计验收失败"。以下差异均为**设计 v0.2 新增、P0 计划未含**：

| # | v0.2 要求 | P0 计划现状 | 影响 | 建议落点 |
|---|---|---|---|---|
| 1 | PPT（`.pptx` / `.ppt`）P0 支持 | `parsers/` 仅 xlsx/docx/pdf/markdown | 用户明确要求的格式缺失 | 新增 Task：`pptx_parser.py` |
| 2 | 扫描件 OCR P0 | 约束写"OCR（P1）"，Task 11 只标 `scanned_pdf` | **"稳定识别字"前提不成立**；存量 PDF 多为扫描件 | 新增 Task：`parsers/ocr.py`，Task 11 接入 |
| 3 | 表单型 / 卡片型（§4.5/4.6/8.9） | 只有 `header_rules.py`，无 `form` 块、无 `detect/form.py` | 审批表/申报表被切成无意义行 | 新增 Task：IR 扩 `form`、`form.py`、切片分支 |
| 4 | 解析体检报告（§7.7） | 无 `quality` 字段/表/接口 | **"稳定"不可度量，退化无法发现** | `schema.sql` 加 `doc_versions.quality`；新增 Task |
| 5 | 假文本层 / 数字保真（§7.1/7.3/7.4） | 无 | 乱码入库、身份证号截断无人知晓 | 并入 Task 3 sniff 与 Task 11 |
| 6 | 分层门禁 L0–L3（§13.1） | Task 24 只有 FAISS vs pg 的检索门禁 | 解析退化拦不住，被误判为"模型效果差" | Task 24 扩为四层指标 |
| 7 | 双跑一致性 `structural_hash`（§7.8） | 无 | 幂等与去重无验证 | Task 24 增加双跑比对 |
| 8 | 格式白名单：`.xls` / `.csv` / 图片 | 无 | 客户存量格式直接拒收 | Task 3 白名单、Task 5/11 分支 |

> 最小对齐动作（不需要写业务代码）：更新任务索引、文件结构、`Global Constraints` 中的"OCR（P1）"，并在 `ingest/ir.py` 设计里补 `form` 块与 `quality` 字段。**IR 与 schema 先改，其余任务才能不返工。**

## 2. P0（含 v0.2 补齐）之后的能力边界

| 可以做 | 做不到 |
|---|---|
| docx / xlsx / pdf（文本层 + 扫描件）/ pptx / 图片 / csv 解析 | OFD、WPS 原生格式、ZIP 批量、邮件 |
| 报表型 + 表单型结构识别、复核、模板复用 | 卡片型无模板时自动识别（一律进复核） |
| 字符保真、OCR 置信度、精度丢失检测与拒识 | 图表/图片的语义问答（只当文本或截图处理） |
| 切片、嵌入、pgvector 混合检索、ACL、引用回源 | Rerank、跨语言检索、数值计算问答 |
| 版本、激活、下线、删除、审计 | 真实身份认证、组织架构同步、细粒度授权 |
| 33 条种子评测 + L0–L3 门禁 | ≥100 题库、注入样本集、客户基准集 |

**一句话**：P0 结束 = "能把文件变成可检索、可回源、可审计的知识"，不等于"能做业务问答"。数值计算、图片理解、权限精细化都还在后面。

## 3. 缺口分类

### 3.1 第 0 类：文档一致性（不写代码即可完成）

- [ ] P0 计划与设计 v0.2 对齐（第 1 节 8 项）
- [ ] `ingest/ir.py` 补 `form` 块与 `quality` 引用，`schema.sql` 补 `doc_versions.quality`
- [ ] 明确"P0 是否含 OCR"——它直接决定工期 4 周还是 6 周
- [ ] 在计划里补"夹具集"任务（见 3.2 最后一条）

### 3.2 第 1 类：上生产必需（P0 之后立即补）

| 项 | 缺了会怎样 | 最小可用做法 |
|---|---|---|
| **真实身份与角色** | 现在只有演示 Cookie + 硬编码账号，政务无法上线 | 接 CAS/OAuth2/LDAP 之一；`users.py` 改适配器；角色落库 |
| **部门/组织架构同步** | `dept` 是自由字符串，改名/撤并后权限失配 | 从身份源同步部门树，`dept` 改 `dept_id` + 显示名 |
| **备份与恢复一致性** | 只备库不备原件，恢复后引用全部 404 | PG + `uploads/` + 索引同点备份；每季度恢复演练 |
| **可观测性** | 客户报"查不到"时无法定位是解析还是检索 | 队列深度、阶段耗时、失败率、`char_fidelity` 分布、复核率 |
| **批量导入工具** | 万份级导入只有单文件交互式上传，无法交付 | CLI 批量导入 + 断点续传 + 失败清单 + 重跑 |
| **保留与销毁策略** | 政务要求到期下线、销毁留痕，P0 只有墓碑行 | 保留期配置 + 到期任务 + 销毁审计 |
| **容量与压测结论** | 无法给客户报硬件清单与工期 | 10 万份规模的嵌入吞吐、PG 内存、HNSW 构建时间实测 |
| **夹具集（50–100 份）** | 所有阈值都是猜的，门禁没有分母 | 客户真实文件 + `header_rows/columns`、`form.fields`、`char_fidelity` 标注 |

### 3.3 第 2 类：P1 已规划（设计 §14）

OCR 精度打磨（倾斜 / 盖章 / 低质页）、WPS 与 OFD、ZIP 批量与邮件、Rerank、评测门禁扩容、监控告警、批量重跑、模板跨部门复用。

### 3.4 第 3 类：P2 与架构级风险

- 表格登记 + Text-to-SQL（数值问答）
- 表单字段级检索与校验
- 多租户 / SaaS
- **信创适配**：麒麟 / 统信 / 达梦 / 人大金仓

> 信创不宜默认排到 P2。政务客户一旦提出，`pgvector + Ollama` 的组合要重新评估（达梦没有 pgvector 等价物，向量检索可能需外部组件）。这属于**架构级风险**，应在第一个政务项目立项时就确认，而不是实施期才发现。

### 3.5 第 4 类：文档未覆盖，但决定"好不好用"

| 项 | 问题 | 建议 |
|---|---|---|
| **答案忠实度校验** | 现在只保证"有引用"，不保证"引用支持结论"，幻觉仍会漏出 | 生成后做一次引用-结论蕴含校验，不通过则降级为"未找到依据" |
| **多版本内容去重** | 同一文件 v1/v2/v3 都在库，检索返回三份近似结果挤占 Top-K | 检索侧按 `document_id` 去重，仅保留当前版本 |
| **术语与同义词词典** | 简称、文号、机构旧称（"市监局" vs "市场监督管理局"）向量命中低 | 检索前同义词扩展，或建同义词表进 `tsvector` |
| **数值与单位归一** | "120 万元" vs "1,200,000 元" 无法比较 | 表格 IR 已有 `unit`，检索/问答前统一换算 |
| **文档过期提醒** | 生效日期到期后仍被当作有效依据 | 到期降权或自动下线，检索返回时标注有效期 |
| **自动通过的人工抽检** | `auto_precision ≥99%` 是抽样结论，精度会缓慢漂移 | 每月抽检 1%，异常触发阈值重校 |

## 4. 下一步：三条并行线

| 线 | 内容 | 是否写代码 | 预估 |
|---|---|---|---|
| **A. 计划对齐** | 第 1 节 8 项落入 P0 计划；IR/schema 先行确定 | 否 | 0.5–1 天 |
| **B. 夹具与摸底** | 收集 50–100 份真实文件；摸底扫描件占比；定 L0–L3 标注口径 | 否 | 1–2 天 |
| **C. M1 实施** | schema / 队列 / 上传 / sniff / 解析器 / IR / 体检报告 | 是 | 按计划 |

**建议顺序：A 与 B 并行 → 再开 C。**

- 不做 A，C 会按 v0.1 产出，`form` 块与 `quality` 字段的缺失会牵动 schema、切片、接口、测试，返工成本最高。
- 不做 B，`HEADER_ACCEPT=0.75`、`CHAR_FIDELITY_MIN=0.995`、`OCR_REJECT_CONFIDENCE=0.4` 全是拍脑袋值，门禁**能跑但挡不住退化**。

## 5. 最容易被低估的三件事

1. **扫描件占比**。若客户存量 >50% 是扫描件，OCR 就是主战场，工期与准确率承诺都要重估——这不是"加个 PaddleOCR"的量级。
2. **复核人力**。`review_rate ≤5%` 是稳定后目标，首批 30% 意味着 1000 份里 300 份要人看。这是运营成本，越早与客户对齐越好。
3. **"解析成功"的假象**。Excel 最典型：不报错、结果全错。体检报告与分层门禁不是锦上添花，而是**唯一能在客户发现之前暴露问题的手段**。

## 6. 待决策清单

| # | 议题 | 影响 | 建议默认 |
|---|---|---|---|
| 1 | 客户扫描件占比 | 决定 OCR 是否成为 P0 主要工作量 | 先摸底再定；>50% 单列 OCR 子里程碑 |

| 3 | `.xls` 是否 P0 | 存量客户格式覆盖 | 含（`xlrd` 成本低） |
| 4 | 信创是否立项即要求 | 架构选型（pgvector 可用性） | 立项即确认，不拖到实施 |
| 5 | 复核由谁承担 | 运营成本与 SLA | 客户方复核，我方提供台与培训 |
| 6 | 密级由谁定 | 上传者定 vs 管理员定 vs 规则继承 | 上传者初定 + 复核确认；模板不继承密级 |
| 7 | 拒答阈值是否对外公布 | 已在前端脱敏 | 内部口径，不写入客户文档 |
| 8 | 首批交付范围 | 是否含复核台前端 | 含（否则复核率无法落地） |

## 7. P0 完成判定（Definition of Done）

在现有计划 24 个任务之外，满足以下条件才可称 "P0 完成"：

- [ ] 设计 v0.2 的 8 项差异全部落地（第 1 节）
- [ ] 四格式（docx / xlsx / pdf / pptx）+ 扫描件 PDF 夹具各 ≥3，双跑 `structural_hash` 一致
- [ ] 体检报告 100% 生成；拒识样本 100% 带明确错误码，无半成品 IR 入库
- [ ] 假文本层零漏检；长数字精度丢失列 100% 检出
- [ ] L0–L3 门禁进 CI：L0 `char_fidelity` 中位 ≥0.995、L2 `header_exact` ≥0.80、`form_field_f1` ≥0.85
- [ ] 50 份真实样本 `parse_success` ≥98%，失败原因可读
- [ ] 既有 203 条测试全绿；33 条检索评测退化 ≤3%，越权泄露 0
- [ ] 上传 50 MB 不阻塞问答；队列满返回 429
- [ ] 备份恢复演练通过一次；部署包与运维手册可交付
